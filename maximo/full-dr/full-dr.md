# Full DR 

We call full DR the restoring of your Maximo instance on another cluster.

We assume that you have on this new cluster all the Kasten restorepoints
created on the previous cluster, either through an [import policy](https://docs.kasten.io/latest/usage/migration/) or through a Kasten [disaster recovery action](https://docs.kasten.io/latest/operating/dr#dr-recovery). Those topics are not the subject of this document.

# General approach 

Restoring on the new cluster by applying all the restorepoints in a single action does not work. 

That would be indeed the ideal approach and the least complex, but it does not align with the relative complexity of the Maximo application:
- Installation of Maximo follows a strict pipeline, and reapplying all the manifests
blindly without taking into account this pipeline order does not work
- Not only does the pipeline follow a strict order, but a lot of objects are created by
operator controllers. This creates a complex chain of dependencies between objects. Restoring them all together creates a simultaneous children-and-parent birth, leading to potential reconciliation errors.
- Many certificates managed by the cert-manager instance installed on your
previous OpenShift cluster will no longer be valid, leading to complex rebuilding and reconfiguration of your application.

The approach consists in re-installing (not restoring) Maximo with the same
configuration that was used on your previous cluster. Then you restore component by component. We'll describe those steps in the rest of this document.

# Reinstall Maximo on the new cluster

Depending on how you installed Maximo, with a fully DevOps-maintained pipeline or using the CLI, apply the same installation process on the new cluster. Once your new Maximo installation is ready you can proceed with the restore of the different components.

# Restore the components on the DR 

You must follow this order for the component you need to restore.

## 1. Namespace that you should not restore in case of DR

This list of namespaces should not need to be restored/overwritten because their initial install on the DR site is often sufficient:
- ibm-sls because you reuse your current license during the install of the DR
- cert-manager-operator because it's fully reinstalled and there is nothing specific between the DR and the source
- cert-manager — see explanation below
- grafana because this is standard dashboard created by the mas installer that you usually don't change, if you change them then you can follow [those steps](../mascore/readme.md#for-cert-manager-and-grafana)

### Why cert-manager should not be restored

Restoring cert-manager artifacts is useful when you restore on the same cluster but not in DR scenario.

In this MAS deployment, cert-manager holds two cluster-specific CA keypairs:

| Secret | Namespace | Used by |
|---|---|---|
| `instance1-cert-internal-ca` | `cert-manager` | `ClusterIssuer mas-instance1-core-internal-issuer` — signs all ~30 internal service certs across `mas-instance1-core` and `mas-instance1-manage` |
| `instance1-cert-public-ca` | `cert-manager` | `ClusterIssuer mas-instance1-core-public-issuer` — signs public-facing MAS routes |

These CA private keys are unique to the source cluster. However, **nothing stored inside the application databases references these CA certificates directly**. They are used only for in-flight TLS between pods — the MAS Core operator provisions them, distributes the CA bundle to pods via cert-manager `Certificate` resources, and re-provisions them automatically on any fresh install.

Each other component (DB2U, MongoDB, SLS) has its own **self-contained** CA chain living entirely within its own namespace, backed by a `selfSigned` issuer:

```
selfSigned Issuer (db2u ns)    → db2u-ca   → db2u-certificate-mas-instance1-workspace1-manage
selfSigned Issuer (mongoce ns) → mongo-ca  → MongoDB service certs
selfSigned Issuer (ibm-sls ns) → sls-ca    → SLS service certs
```

These are regenerated by their respective operators when those namespaces are freshly installed on the DR cluster.

**The DB2U case deserves special attention.** The cert-manager-issued `db2u-certificate-mas-instance1-workspace1-manage` (in the `db2u` namespace) is the certificate the DB2U engine presents to JDBC clients. The JDBC entity manager operator copies this public certificate into the `JdbcCfg` CR in `mas-instance1-core`, from where Maximo Liberty pods load it into their SSL truststore. On a fresh DR install, cert-manager generates a new `db2u-ca` and a new service cert — and the JDBC operator automatically picks up the new cert and updates the `JdbcCfg`.

This is precisely why the DB2U restore blueprint **does not restore the `bludb_ssl.kdb` SSL keystore** on the DB2U meta PVC: the keystore (which holds the private key matching the service cert) must stay in sync with what cert-manager generated for this cluster. If the old keystore were restored, DB2U would present the old cert while cert-manager has issued a new one — SSL handshake failure. The rule is: let cert-manager own the cert lifecycle, restore only the data.

**The reinstall approach makes cert-manager restoration unnecessary and even harmful.** When MAS Core is reinstalled on the DR cluster, the MAS operator generates a fresh `instance1-cert-internal-ca` and all service certificates are re-issued from it — everything is internally consistent from day one. If you instead restored the old `cert-manager` namespace on top of a fresh DR OpenShift cluster, you would have old CA keypairs in cert-manager but new cluster infrastructure (new service accounts, new OpenShift router certs, etc.), creating a mixture of old and new trust anchors that is very hard to untangle.

> **Rule of thumb:** cert-manager state is a function of which operators are running, not of what data is in the databases. Because the reinstall recreates the operators, the operators recreate the cert-manager state correctly. Restoring cert-manager is only necessary for a pure Kasten "restore everything" approach — which is explicitly not the strategy used here.

## 2. Prepare the DR cluster

Set the variables used in the rest of this document. Read them from the MAS labels on the CRs of the reinstalled DR cluster 
rather than typing them, this avoids parsing resource names:

```bash
# list all the instances and workspaces
oc get suite -A -o jsonpath='{range .items[*]}{.metadata.labels.mas\.ibm\.com/instanceId}{"\t"}{.metadata.name}{"\t"}{.metadata.namespace}{"\n"}{end}'
oc get manageworkspace -A -o jsonpath='{range .items[*]}{.metadata.labels.mas\.ibm\.com/instanceId}{"\t"}{.metadata.labels.mas\.ibm\.com/workspaceId}{"\n"}{end}'

# set the variables (single instance and workspace, otherwise pick yours from the lists above)
MAS_INSTANCE_ID=$(oc get suite -A -o jsonpath='{.items[0].metadata.labels.mas\.ibm\.com/instanceId}')
MAS_WORKSPACE_ID=$(oc get workspace -n mas-${MAS_INSTANCE_ID}-core -o jsonpath='{.items[0].metadata.labels.mas\.ibm\.com/workspaceId}')
echo "$MAS_INSTANCE_ID / $MAS_WORKSPACE_ID"
```

They must be the same as on the source cluster: compare them with the names of the Suite and ManageWorkspace (`<instance>-<workspace>`) 
in the source restore points. A mismatch means the reinstall was not done with the same configuration.

On the DR cluster:
- Deploy the [MongoCE blueprint](../mongoce/readme.md#install-and-execute-the-blueprint) and the [DB2u blueprint and its binding](../manage/db2u/README.md#deploying-the-blueprint).
- **Create the `mas-instance-id` configmap in the `mongoce` namespace.** The reinstall does not create it, and we never restore it 
  because only the MongoCE backup PVC is restored. The MongoCE restore hook reads this configmap **on the DR cluster at restore time**:
  - only the instances listed in the configmap are restored, use it to restore a subset of your instances;
  - every instance listed must have a dump in the backup, the dumps were created from the list of the configmap on the source cluster 
    at backup time. If you list an instance that was not in the source configmap, `mongorestore` fails on a missing archive.
  ```bash
  oc create configmap -n mongoce mas-instance-id --from-literal mas-instance-id=${MAS_INSTANCE_ID}
  ```

## 3. Compare the top objects, do not restore them

Maximo has been reinstalled, the top objects already exist on the DR cluster and were generated for this cluster. Check that they are 
in the same state as on the source cluster (same version, same components, same settings), but do not restore or modify them from the 
source backup. Run these commands on both clusters and compare:

```bash
oc get suite -n mas-${MAS_INSTANCE_ID}-core -o yaml | yq '.items[] | {"kind": .kind, "name": .metadata.name, "spec": .spec}'
oc get jdbccfg -n mas-${MAS_INSTANCE_ID}-core -o yaml | yq '.items[] | {"kind": .kind, "name": .metadata.name, "spec": .spec}'
oc get manageworkspace,managedeployment,managebuild -n mas-${MAS_INSTANCE_ID}-manage -o yaml | yq '.items[] | {"kind": .kind, "name": .metadata.name, "spec": .spec}'
```

This is especially true for the `JdbcCfg`: it carries the DB2u certificate and credentials of the DR cluster, restoring the source 
one would break the connection between Manage and DB2u. Certificates and credentials are expected to differ, compare the rest 
(URL, database name, schema, workspace binding...).

If they differ, fix the DR install before you go further.

## 4. Disable the generation of the encryption keys

This is the only change you make to a top object. Set `autoGenerateEncryptionKeys: false` in the ManageWorkspace spec so the operator 
won't overwrite the encryption key that you will restore:

```bash
oc patch manageworkspace ${MAS_INSTANCE_ID}-${MAS_WORKSPACE_ID} \
  -n mas-${MAS_INSTANCE_ID}-manage --type merge \
  -p '{"spec":{"settings":{"deployment":{"autoGenerateEncryptionKeys":false}}}}'
```

## 5. Scale down Manage, then Core

Manage depends on Core (Suite, `JdbcCfg`, license) and on DB2u, Core depends on MongoCE. Stop them from the top of the chain: Manage 
first, then Core, before you restore any database. 

The operators of Core and Manage run as deployments in their own namespace, once a namespace is entirely scaled down its operator is 
scaled down too, and no deployment comes back until you scale it back manually in [step 9](#9-scale-up-core-then-manage).

Save the number of replicas first. The file is not overwritten if it already exists, so that running this again on a namespace already 
scaled down does not save zeros:

```bash
for NS in mas-${MAS_INSTANCE_ID}-manage mas-${MAS_INSTANCE_ID}-core; do
  [ -f "$NS-replicas.txt" ] || oc get deployment -n "$NS" -o custom-columns=NAME:.metadata.name,REPLICAS:.spec.replicas --no-headers > "$NS-replicas.txt"
  oc scale deployment --all -n "$NS" --replicas=0
  oc wait pod --all -n "$NS" --for=delete --timeout=300s 2>/dev/null || true
done
```

Keep `ibm-sls` running: its own MongoDB database is not part of the MongoCE restore and it was registered during the reinstall.

## 6. Restore the Manage encryption secret and PVCs

From the restore point of the `mas-${MAS_INSTANCE_ID}-manage` namespace, with "overwrite existing", select only:
- the secret `${MAS_WORKSPACE_ID}-manage-encryptionsecret`;
- the PVCs, if Kasten is responsible for their backup. If the PVCs are backed up by VBR, restore the files with VBR 
  (see [Manage restore](../manage/manage/readme.md#if-you-manage-the-backup-of-the-pvcs-with-vbr)).

Do not restore any other resource of the namespace.

## 7. Restore the MongoCE database

Follow the [MongoCE restore procedure](../mongoce/readme.md#restoring): configure the post restore hook and restore only the 
`mongoce-backup-pvc`. 

For each instance listed in the `mas-instance-id` configmap, the hook drops and restores `mas_<instance>_core` and 
`mas_<instance>_catalog`. It keeps the `OauthClient` collection of the DR cluster, so the client secrets created by the reinstall 
remain valid.

## 8. Restore the Manage database

If you're using DB2U (built in database for Manage) follow the [DB2U restore guide](../manage/db2u/README.md#on-the-destination-cluster), 
cross instance case, **but skip its scale down and scale up of the Core and Manage namespaces**, they are already scaled down 
and you will scale them up in the next step. Run only the DB2u part: scale down DB2u, import the backup PVC, scale up DB2u, 
import the source encryption key, restore and rollforward.

If you're not using DB2U but an external database, restore the external database with the backup of the production database.

## 9. Scale up Core, then Manage

Start from the bottom of the chain: Core first, wait for the Suite to be ready, then Manage. Use the replicas saved in step 5:

```bash
NS=mas-${MAS_INSTANCE_ID}-core
while read DEPLOY REPLICAS; do oc scale deployment "$DEPLOY" -n "$NS" --replicas="$REPLICAS"; done < "$NS-replicas.txt"
oc wait suite --all -n "$NS" --for=condition=Ready --timeout=1800s

NS=mas-${MAS_INSTANCE_ID}-manage
while read DEPLOY REPLICAS; do oc scale deployment "$DEPLOY" -n "$NS" --replicas="$REPLICAS"; done < "$NS-replicas.txt"
```

Once Manage is `Ready` (see below), delete the `*-replicas.txt` files, otherwise a future restore would reuse these old counts.

This triggers a reconciliation. Check that the ManageWorkspace reaches `Ready`:

```bash
# Snapshot of all conditions — run at any time to see current state
kubectl get manageworkspace ${MAS_INSTANCE_ID}-${MAS_WORKSPACE_ID} -n mas-${MAS_INSTANCE_ID}-manage \
  -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}' \
  | column -t -s $'\t'
```

Expected output when healthy:
```
Ready            Ready      
BuildReady       Build completed   Build generated and tagged with ...
DeploymentReady  Ready      
DeploymentCR     Successful
AcceleratorCR    Ready      Ready to activate accelerators
Failure          <empty>
Successful       Successful Last reconciliation succeeded
Running          Running    Running reconciliation
```

The two fields to watch are:
- `Ready` — must be `Ready` (not `Pending` or `Failed`)
- `DeploymentCR` — must be `Successful` (not `Failed`)

To **watch** until `Ready` transitions to `True`:

```bash
until kubectl get manageworkspace ${MAS_INSTANCE_ID}-${MAS_WORKSPACE_ID} -n mas-${MAS_INSTANCE_ID}-manage \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].reason}' | grep -q "^Ready$"; do
  STATUS=$(kubectl get manageworkspace ${MAS_INSTANCE_ID}-${MAS_WORKSPACE_ID} -n mas-${MAS_INSTANCE_ID}-manage \
    -o jsonpath='{.status.conditions[?(@.type=="DeploymentCR")].message}' 2>/dev/null)
  echo "$(date +%H:%M:%S) Waiting — DeploymentCR: $STATUS"
  sleep 30
done
echo "ManageWorkspace is Ready"
```

If it stays in a failed state, check the `run-db.sh` output inside the maxinstudb pod:

```bash
MAXINST_POD=$(kubectl get pod -n mas-${MAS_INSTANCE_ID}-manage -l mas.ibm.com/appType=maxinstudb \
  --no-headers -o custom-columns=':metadata.name' | head -1)
kubectl logs -n mas-${MAS_INSTANCE_ID}-manage "$MAXINST_POD" \
  | grep -E "status:|Crypto Keys|Query count|BMXAA681[89]|Maximo version"
```

And check the operator Ansible playbook for the workspace:

```bash
kubectl logs -n mas-${MAS_INSTANCE_ID}-manage \
  $(kubectl get pod -n mas-${MAS_INSTANCE_ID}-manage -l app.kubernetes.io/name=ibm-mas-manage \
    --no-headers -o custom-columns=':metadata.name' | head -1) \
  --all-containers --since=10m \
  | grep -E "PLAY RECAP|prepare.db|failed="
```
